# ldk-server fork: Coinbase cb-mpc threshold channel signing for Lightning

**This is a fork of [lightningdevkit/ldk-server](https://github.com/lightningdevkit/ldk-server)
whose only purpose is to test putting Lightning channel keys under Coinbase's
[cb-mpc](https://github.com/coinbase/cb-mpc) threshold MPC.** It is not a release of LDK
Server; for the daemon itself use upstream. Upstream's README, API docs and contribution
guide are unchanged under `docs/`, `ldk-server-grpc/` and `CONTRIBUTING.md`.

## In short

A Lightning node normally keeps every channel key on one machine, so whoever controls that
machine controls the funds. This fork takes every channel key off the LDK Server host and
shares it among several independent *parties* (four in the tests), any three of which must
agree to sign. No party ever holds a whole key. The revocation secrets, which cannot be
shared the same way because they come from a hash chain, exist online only as ciphertexts
that the same three-of-four must agree to decrypt.

Each party is a validator, not a rubber stamp. It rebuilds every commitment from its
balances and HTLCs with keys it trusts, runs the Validating Lightning Signer's rules on it,
verifies the counterparty's signature on every new state itself before an old one can be
revoked, counts what leaves the node's balance against a limit, and refuses to sign old
states, or closes, splices and sweeps to addresses it does not know.

Three of four is the smallest setup that survives one party being down **and** one party
being compromised at the same time: any two groups of three share two parties, so at least
one honest party in every group has seen everything that came before.

This runs real Lightning end to end on regtest: channel open, payments in both directions,
restarts, payments with one party down (including the one LDK Server was talking to),
splices, cooperative close and force-close.

Caveats. It is a proof of concept reviewed by no one but its authors (much of it written
with AI assistance), all parties run on one machine in the tests, and one small
key-derivation helper is added outside cb-mpc's audited public API. The on-chain wallet is
the one key still on the host: channel funds can only be sent into that wallet, but once
there the host can spend them. Do not use this with real funds.

## What it does

- **Channel keys.** The funding, payment, delayed-payment, HTLC and revocation keys are
  generated by cb-mpc's distributed key generation under a 3-of-4 access structure
  (configurable). Per-commitment keys are derived on the shares with the BOLT 3 tweaks.
- **Signing.** LDK Server sends a request to any party. That party leads: it applies its
  policy, picks a quorum and runs cb-mpc's threshold ECDSA with it. Every member applies its
  own policy first. If a member is down or refuses, the leader tries another quorum; if the
  leader is down, LDK Server asks the next party.
- **Revocation secrets.** An offline ceremony tool splits a master seed among custodians and
  makes *channel kits*: public per-commitment points plus each secret encrypted to the
  parties' joint TDH2 key. A secret is recovered only from the partial decryptions of three
  parties whose policy allows the release.
- **Verified state.** A party treats a new holder commitment as validated only after
  checking the counterparty's signature on it and the commitment number it encodes. A host
  that merely claims so gets nothing. A party that was down catches up from the same proof.
- **Links.** Parties authenticate each other with Ed25519 identity keys over encrypted
  links; key shares are encrypted at rest. All Lightning channel state stays in LDK Server.

Details, diagrams and the threat model are in
[`ldk-server-mpc/README.md`](ldk-server-mpc/README.md).

## Which secrets exist, and where

"The seed" below means one thing only: the seed of the revocation secrets. The channel keys
have no seed and are never whole anywhere.

| Secret | What it is for | Where it lives | Ever whole on one machine? |
|---|---|---|---|
| Channel keys (funding, payment, delayed-payment, HTLC, revocation basepoint) | Signing everything a channel signs | One share per party, made jointly when the channel opens | **No, never.** There is no seed and no backup phrase for them |
| Revocation secrets (per-commitment secrets) | Revoking our old channel states, one secret per state | Encrypted in the kit files every party holds; three parties must agree to decrypt one | Only as the **master seed**, on the offline ceremony machine, for the length of a ceremony run |
| Master seed pieces | Rebuilding the master seed for a ceremony | One piece per custodian, offline | A piece alone reveals nothing; any `threshold` of them rebuild the seed |
| TDH2 key | Decrypting revocation secrets | One share per party, made jointly | No |
| On-chain wallet mnemonic | The node's on-chain wallet, where closes and sweeps pay | The LDK Server host | **Yes, on the host.** Not yet behind the parties |
| Node identity key | The node's Lightning identity (gossip, invoices, onion) | The LDK Server host | Yes, on the host. It cannot move channel funds |
| Party identity keys, share keys, client key | Links between the parties and LDK Server; encrypting shares at rest | Each party's own files | Each on its own party |

So the ceremony, and the seed, are about revocation secrets and nothing else. BOLT 3 makes
those come from a hash chain, which cannot be computed on shares the way a signature can;
that is why they need a seed at all, and why it is kept offline and split.

## Getting started

In the order things have to happen. For a trial everything can run on one machine; for the
split to mean anything, each party needs its own machine and its own operator.

**You need:** four machines for the parties (called a, b, c, d here), the LDK Server host,
an offline machine for the ceremony, and a **fresh node**. MPC cannot be switched on for a
node that already has channels.

### 1. Build

Build cb-mpc, the patched ldk-node, and this repository. The commands are in
[`ldk-server-mpc/README.md`](ldk-server-mpc/README.md#building). The result is three
binaries besides LDK Server: `ldk-server-mpc-party`, `ldk-server-mpc-ceremony` and
`ldk-server-mpc-bench`.

### 2. Each party makes its identity

On each party's machine:

```bash
ldk-server-mpc-party --keystore mpc/a --share-key-file keys/share-a.key --print-identity
```

It prints the party's public identity key. The operators exchange these four keys; they are
what the parties recognize each other by. Together with the addresses they form the
*roster*, which is the same on every party, in the same order:

```bash
ROSTER="--threshold 3 --party a=10.0.0.1:7711=<id a> --party b=10.0.0.2:7711=<id b> \
  --party c=10.0.0.3:7711=<id c> --party d=10.0.0.4:7711=<id d>"
```

### 3. Start one party, then LDK Server

LDK Server needs to reach a party to start, and the parties need LDK Server's wallet
address list to know where channel funds may be paid. So one party goes first:

```bash
ldk-server-mpc-party --name a --listen 10.0.0.1:7701 --keystore mpc/a $ROSTER \
  --auth-key-file keys/client.psk --share-key-file keys/share-a.key --network bitcoin
```

`keys/client.psk` is created here. Copy it to the LDK Server host and to the other parties:
it is the key of the link between LDK Server and the parties.

Then LDK Server, on a fresh storage directory, with this in its config:

```toml
[node]
onchain_wallet_mnemonic_path = "/path/to/onchain_wallet_mnemonic"

[mpc]
party_address = "10.0.0.1:7701,10.0.0.2:7701,10.0.0.3:7701,10.0.0.4:7701"
coverage = "all"
auth_key_path = "/path/to/client.psk"
```

On its first start it writes `<storage>/onchain_wallet_xpub`: the public key of its
on-chain wallet.

### 4. Start all four parties

Stop party a, and start all four with the wallet's public key and the limits you want:

```bash
ldk-server-mpc-party --name a --listen 10.0.0.1:7701 --keystore mpc/a $ROSTER \
  --auth-key-file keys/client.psk --share-key-file keys/share-a.key --network bitcoin \
  --payout-xpub "$(cat onchain_wallet_xpub)" \
  --max-outflow-sat-per-day 5000000
```

- `--payout-xpub` is the only place closes, sweeps and splice-outs may pay.
- `--max-outflow-sat-per-day` is the most that may leave the channel balances in a day.
  Leave it out and there is no limit.

Once all four are up they generate their joint TDH2 key by themselves, and each writes its
public half to `<keystore>/tdh2.pub`. No channel keys exist yet.

### 5. The ceremony: revocation secrets (offline)

On the offline machine, with `tdh2.pub` carried over. The first time only, create the
master seed and split it among custodians (here any 3 of 5):

```bash
ldk-server-mpc-ceremony new-seed --threshold 3 --pieces 5 --out-dir pieces
```

Hand one piece file to each custodian and note the fingerprint it prints. The seed itself is
not stored. Then, with three custodians present, make kits, one per channel you expect to
open:

```bash
ldk-server-mpc-ceremony new-kits --piece piece-1.txt --piece piece-2.txt --piece piece-3.txt \
  --fingerprint <from new-seed> --tdh2-public-key tdh2.pub \
  --kits 10 --states 50000 --out-dir kits
```

During this command the seed is whole in that machine's memory. That is the one moment it
is. The kit files that come out hold only public points and ciphertexts: carry them back and
copy every one to every party's `<keystore>/kits/` directory.

### 6. Open a channel

With **all four parties up**, open a channel through LDK Server as usual. The parties
generate the channel's five keys among themselves and bind one kit to the channel. A
channel cannot open with a party down, or with no unused kit left.

### 7. Run

From here any three parties are enough: payments, forwards, closes and force closes all
work with one party down, including the one LDK Server happens to be talking to. A splice
makes a new funding key, so like a channel open it needs all four. Each party refuses what
its own policy does not allow, whatever LDK Server says.

### 8. Keep it running

- **Refill kits before they run out.** A kit covers the number of states it was made with;
  a channel stops when its kit is used up. The leading party warns below 256 states left.
  A refill is another ceremony run with the custodians: `ldk-server-mpc-ceremony refill`.
- **Make kits before opening more channels.** One unused kit per new channel.
- **Back up each party's keystore, each on its own.** A party that loses its keystore
  cannot rejoin: the others will not regenerate a key. With two keystores lost, the channel
  keys are gone.
- **Allow-list an address before splicing out to it** (`--payout-address` on every party).
- **Set the outflow limit above what the node really sends.** At the limit the parties stop
  signing and the channel waits until the window has room.

The full reference, with the architecture and the threat model, is
[`ldk-server-mpc/README.md`](ldk-server-mpc/README.md).

## Status (2026-11-10, branch `mpc`)

What is built, in the order it went in:

1. **Revocation secrets.** Made offline from a seed split among custodians, stored
   threshold-encrypted, released only after the parties have checked the counterparty's
   signature on a newer state.
2. **Three-of-four signing.** Every channel key is a distributed key. Each party checks every
   request against its own record before it takes part.
3. **Signing speed, measured.** About 400 ms per signature with three parties sharing a
   two-core test machine; the signatures of one request run side by side. Most of the time
   is oblivious transfers that the protocol redoes for every signature. See
   [`docs/mpc-benchmarks.md`](docs/mpc-benchmarks.md).
4. **Splices.** The parties follow a channel only to a funding output that a splice they
   signed creates, and refuse a splice that pays our balance to an address they do not know.
5. **No revoking what was signed.** A state signed for broadcast is never revoked.
6. **The VLS validator in every party.** Each commitment is rebuilt from its balances and
   HTLCs and judged by the
   [Validating Lightning Signer](https://gitlab.com/lightning-signer/validating-lightning-signer)'s
   rules. An outflow limit caps what may leave our balances per hour or day, by any route.

How it is tested:

- **Regtest, four party processes:** `e2e-tests/tests/mpc.rs`. Channel open (five key
  generations), payments both ways, restart of all parties, payments with one party down and
  with the leading party down, restart of LDK Server, cooperative close, holder force-close,
  splice-in, a splice by the counterparty, splice-out, a splice-out three parties refuse
  against a fourth that sides with the host, and a payment refused at the outflow limit.
  The kits are made by the real ceremony tool.
- **Party tests:** `cargo test -p ldk-server-mpc`. Every quorum signing and decrypting, LDK's
  own shachain store accepting released secrets, a compromised host, a compromised party, a
  party that missed updates or a splice, a forged transaction behind a true description.
- **Not run on signet or mainnet,** and never on separate machines. The earlier two-party,
  funding-key version ran on signet ([`docs/mpc-signet-demo.md`](docs/mpc-signet-demo.md)).

## How far this gets

The goal is a Lightning node that no single machine can rob. Scored honestly, from 0 (does
not help) to 10 (solves it decently well): the design is about a 7, and what is built is
about a 6 with the outflow limit set, 4 without it.

A compromised LDK Server host can no longer sign away a channel, revoke a live state, close
or splice to its own address, or get anything signed that is not a real commitment of the
channel. What it can still do is listed next.

## What remains

Theft paths still open:

- **Lightning payments, up to the limit.** The parties never see invoices, so they cannot
  tell a payment the operator meant from one a compromised host made up. The outflow limit
  (`--max-outflow-sat-per-day`) bounds both alike, and it is off unless set.
- **The on-chain wallet** is still a key on the LDK Server host. Channel funds can only be
  paid into it, and then the host can spend them.
- **The seed of the revocation secrets.** Only those come from a seed; the channel keys do
  not. It is split among custodians, but whole on the offline ceremony machine for every
  run, refills included. With it, a counterparty can take a channel the moment we
  force-close.
- **One operator, one codebase.** Four parties running the same software under one
  administrator are one target. They are a trust boundary only on separate infrastructure
  with separate operators.
- **No review.** Nobody outside has looked at this. `derive_mul_add_ac` and the threaded
  oblivious transfers are patches outside cb-mpc's public, bug-bounty-covered API.

Things that do not work well yet:

- **Opening a channel needs all four parties up**, and key shares are never rotated.
- **A refusal stalls the channel.** A splice the parties refuse midway stays pending, and a
  commitment refused at the outflow limit stops all updates until the window has room.
  Recovery from a stuck splice is not worked out; a force close is the fallback.
- **VLS's limits are its defaults:** 10 BTC per channel and about 0.168 BTC of HTLCs in
  flight. They are not configurable here yet.
- **Fee-bumping a pending splice** has not been run with MPC.
- **Kits run out.** A kit covers a fixed number of channel states and must be refilled by
  the ceremony before it does.

Next, in this order: configurable VLS limits, the wallet behind the parties, share rotation,
a signet run on separate machines. Further out: reusing oblivious transfers across
signatures (roughly half the signing cost, needs a cryptographer), and dropping the seed for
peers that support independent per-commitment secrets, if that reaches upstream lnd and
Core Lightning.

Details are in [`ldk-server-mpc/README.md`](ldk-server-mpc/README.md).

## Where things are

- [`ldk-server-mpc/`](ldk-server-mpc/): cb-mpc bindings, party service, client, policy,
  mesh links, kits and the ceremony tool. Its README has the architecture and threat model.
- [`ldk-server/src/mpc_signer.rs`](ldk-server/src/mpc_signer.rs): LDK Server's signer;
  `[mpc]` config in [`docs/configuration.md`](docs/configuration.md).
- [`contrib/patches/`](contrib/patches/): the ldk-node patch (`ExternalChannelSigner`,
  separate wallet entropy, `signer_unblocked` poke, commitment details for the signer) and
  the two cb-mpc patches (key derivation on shares, optional threaded oblivious transfers). The
  workspace `Cargo.toml` expects the patched ldk-node at `../ldk-node` and cb-mpc at
  `../cb-mpc`.
